# Parallel transfers

The Internet downloader schedules verified 8 MiB ranges across a bounded pool (4 starting / 8 maximum desktop, 2 starting / 4 maximum Android Go, maximum configurable 1–16 via NODEXLM_DOWNLOAD_CONNECTIONS). Large files require a strong ETag and expected SHA-256; unsupported range responses fall back to the existing sequential implementation. Each worker writes directly into a separate sparse staging file, with durable checkpoints after sync. Final verification precedes publication. No whole-model buffers or joining step. Web download details show active ranges, observed network byte rate and approximate ETA (rate includes retries, so ETA is advisory). Admission grows after successful ranges and shrinks on HTTP 429/503 or observed disk-write bottlenecks; Retry-After is shared by the workers. This is conservative congestion control, not a measured optimal throughput estimator. NODEXLM_DOWNLOAD_LIMIT_BPS caps aggregate bytes per second across ranges and shards. Dashboard reduces it to 2 MiB/s while the primary manager is loading or generating, preserving bandwidth for inference; idle residents do not throttle downloads.

The pinned llama.cpp patch previously drained its workers at the end of each load_all_data call. Upstream calls that function per buffer context, often one per RPC device. The replacement shares workers across the entire load (up to eight RPC devices); the last context drains before unmapping. Load progress subtracts queued but unfinished mapped bytes. Native logs report worker count and peak concurrent tensor calls; this is not a direct measurement of network overlap. Commands to one device remain ordered; the RPC endpoint dispatcher still serializes same-endpoint traffic. Mapped and ordinary buffered file loads supported; the latter reads in 1 MiB chunks per active worker with a shared file-cursor mutex. Explicit direct I/O and check-tensors modes remain on the original path. Chunked writes and cache behavior require native acceptance testing. Existing published r5 remains pinned until r6 artifacts are verified and promoted. To test the new native patch locally, use NODEXLM_MODEL_WIDE_RPC_BUILD=1 nodexlm host; this requires a source build toolchain. Set NODEXLM_PARALLEL_RPC_UPLOAD=0 for comparison.

CLI and Web sharded Hugging Face downloads share one metadata planner and resolve X-Repo-Commit and per-file sizes, then transfer up to four shards under the shared connection ceiling. All stages verify before the first shard is published last. Unavailable revision metadata retains the legacy sequential path. Admission conservatively requires free disk for the full set, even when some stages exist.

Android model downloads now resolve each shard to a single immutable Hugging Face commit, require SHA-256 and pinned shard sizes from HTTPS HEAD metadata, and verify all bytes before publication. Models without a verifiable digest are rejected instead of being accepted on GGUF magic alone. DownloadManager is still the transport, so there is no claim of native Rust downloading or per-connection telemetry.

Optional official Xet CAS acceleration: set NODEXLM_DOWNLOAD_XET=1 on desktop/Host and install the supported Hugging Face `hf` CLI with hf-xet enabled. Only immutable commit-pinned GGUF URLs with content SHA-256 and size metadata are eligible. The CLI writes into an isolated temporary directory and the entire output is rehashed before staging, so failure can safely fall back to the internal HTTPS downloader. No new dependency or Python process is started by default. Xet download progress is currently reported upon verification, not per connection. The APK uses DownloadManager and now reports observed transfer rate and approximate ETA (neither is native per-connection telemetry).

Authenticated local content cache (opt-in): NODEXLM_MODEL_P2P=1 on the Host records verified SHA-256-indexed published models and allows only enrolled Guests to fetch /v1/nodes/cache/{sha256} over the existing pinned TLS endpoint. The Host rehashes cached files before serving, supports HTTP ranges, and never accepts a filename from the node. Android uses the paired certificate and node token to attempt an already verified shard from this Host cache; a cache miss falls back to HTTPS Hugging Face. This avoids repeated WAN transfer when the Host already owns an identical published GGUF. This is Host-to-Guest sharing, not a complete decentralized Guest-to-Guest mesh.

Not yet implemented: Android native Rust DownloadManager replacement, direct Guest-to-Guest discovery/cache sharing, per-connection native APK telemetry. Direct Xet CAS implementation inside the APK remains pending. Real throughput and mixed-device loading overlap must be measured before claiming improvement.

Dashboard: one card per registered device, with native disclosure for management tools; loading status joins the admitted placement and actual RPC counters by authenticated node ID, renders names and approximate progress, and hides redundant topology until ready. The chat has a bounded history and compact composer; the overview displays the resident model name.

Opt-in local SHA-256 deduplication: NODEXLM_MODEL_DEDUP=1 indexes verified published files in the managed library and rehashes an existing candidate before linking the new name. This saves disk space after download, not WAN traffic. Both aliases share an inode; use only immutable trusted model files. No index entry retains a second weight copy.

Chat metrics: native decode uses predicted_n / predicted_ms (all generated tokens, including reasoning). End-to-end rate uses completion_tokens or the runtime's predicted_n when usage is absent. Separate reasoning and non-reasoning counts are shown only if completion_tokens_details.reasoning_tokens is actually supplied and valid. The pinned llama.cpp server-task.cpp currently reports n_decoded as completion_tokens without separate reasoning usage. Observed first output, visible text and reasoning event window are wall-clock SSE timings, not exact per-token phase speeds. Metrics are in a compact disclosure, not a scrolling page.
