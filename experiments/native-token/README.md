# Native token activity diagnostic candidate (P2)

Pinned llama.cpp v1.0.0, opt-in via NODEXLM_NATIVE_TOKEN_TRACE=1. Native accepted token events identify task, slot and ordinal, never prompt, vocabulary token ID or text. Native scheduler events identify actual successfully submitted graph splits, backend and node count, correlated by an explicit thread-local batch identifier. No additional synchronization or RPC wire changes. Batch identifiers are process-local; logs can include native backend names and are diagnostic/private.

Only one-slot, one-input, non-speculative, non-first generation tokens are marked attributable. Prefill and speculative/multiple-slot work is not attributed to individual output tokens. Submission counts are not hardware utilization or device compute time; the trace must not be presented as such. Callback-evaluation graph splits are excluded. The signed/published r5 binaries and Android remain uninstrumented. The canonical patch is now in internal/llamaruntime/patches/native-token-activity.patch. Setting NODEXLM_NATIVE_TOKEN_TRACE=1 on the Host requests an isolated source-built pinned runtime with the trace patch (requires local compiler, CMake and Git). An explicitly supplied instrumented llama-server can also emit the same trace. Leave the flag unset for ordinary runs. The authenticated /api/inference/activity endpoint and Web dashboard show the latest 16 attributable tokens, with native backend names and counts of graph submissions. No background polling or trace allocation when the flag is unset. Initial native acceptance was local CPU; combined source-build, physical distributed verification remains required before enabling by default.

For a loaded distributed topology, the dashboard now associates an RPC graph submission with a Guest only when its native backend name contains the exact admitted relay endpoint. The upstream per-server device index alone is not unique across Guests. Unmatched endpoints are not assigned to any node; private relay paths are removed from the displayed backend name. This reports actual submitted graph splits under the same single-slot attribution restrictions, not remote execution duration or utilization. The mapping is covered by deterministic tests; physical distributed acceptance is still required.

The candidate additionally emits `decode_us` from a native steady clock around `llama_process` and its required output synchronization. The dashboard shows it only for attributable tokens; this is batch wall time, including scheduling, RPC waits and diagnostic logging, not per-device kernel timing or end-to-end token latency. Older diagnostic builds omit the field. No clock is read when tracing is disabled. The CPU candidate gate checks the field on real generation; distributed physical validation remains separate.
